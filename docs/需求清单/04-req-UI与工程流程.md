## 一、逐条要点

### 第六节 UI 要求（L100–106）

- **六.1**（L102）：一套轻量控制界面，分组提供四个维度的切换：场景、车型、时间、天气（共四组）；每组用「图标 + 文字」的分段按钮或卡片列表（两种形式任选其一）；当前选中态清晰。
- **六.2**（L103）：顶部或角落显示当前组合标题，示例格式为「山间松林 · 拖挂房车 · 夜间 · 小雨」（即 场景 · 车型 · 时间 · 天气，以「·」分隔）。
- **六.3**（L104）：UI 风格与三渲二美术统一：半透明磨砂玻璃质感、圆角、细描边、柔和阴影、轻快的悬停 / 选中微动效；整体小巧克制，不遮挡模型主体。
- **六.4**（L105）：提供「隐藏 / 呼出 UI」入口，可回到纯观赏模式（呼应原始「无 UI 陈列感」的精神，另见一.4 L10）。
- **六.5**（L106）：切换逻辑三条——①场景与车型切换用短暂淡入淡出 / 滑动过渡；②时间与天气切换用光照与粒子的平滑过渡；③相机拖拽旋转 / 缩放状态在切换前后保持连续，不打断观看。

### 第八节 技术约束与工程要求（L118–124）

- **八.1**（L120）：本机已安装 node 与 pnpm，使用 pnpm 作为包管理器；技术栈建议 Vite + Three.js（TypeScript 优先）；纯浏览器运行，运行时不依赖网络。
- **八.2**（L121）：严禁使用 Blender 及任何外部建模软件 / DCC；所有几何体用代码程序化生成（基本体、Lathe / Extrude、实例化复用）；三渲二效果用卡通材质 + 渐变色阶 + 描边实现（反壳描边或后期描边均可）；所需贴图用 Canvas / SVG 程序化生成。
- **八.3**（L122）：性能目标：中端笔记本 60fps；重复元素（松树、礁石、集装箱、行道树、桌椅等）使用实例化，控制 Draw Call。
- **八.4**（L123）：架构上把场景 / 车型 / 时间 / 天气做成四套互相独立的注册表与数据模块（见 2.5 L42–44、3.6 L75–77）；公共系统（风力、粒子、灯光呼吸、描边、时间光照预设、天气材质状态，共 6 项）沉淀为可复用模块，支持后续持续扩展。
- **八.5**（L124）：画布自适应窗口尺寸；交互支持鼠标与触屏（拖拽旋转、滚轮 / 双指缩放）。

### 第九节 工作流程要求（硬性约束）（L126–139，整节标注为硬性约束）

- **九.1**（L128）理解先行、文档先行：
  - 读完提示词后不要立即开始实现，更不要先斩后奏地搭建工程；
  - 第一步是通读全文、梳理对需求的理解，并产出一份详细的实现文档（如 DESIGN.md）提交用户审阅；

  - 该文档经用户审阅并获得明确同意后，才能进入编码实现阶段；在此之前不进行任何编码、脚手架搭建或依赖安装；
  - 审阅提出的修改意见，需先回写到实现文档完成修订，再继续推进。
- **九.2**（L129）浏览器使用约束：开发全程的页面预览、打开与调试，仅允许使用自带的内置浏览器 / 内置预览调试能力完成（运行验证、页面截图、控制台调试均在其中进行）；严禁启动系统安装的浏览器（Chrome、Edge、Firefox 等），也不要通过系统默认浏览器或 `start` / `open` 之类的命令打开页面。
- **九.3**（L130）按需复盘、对照纠偏：
  - 每完成一个阶段性模块（某个场景、某款车型、某套系统或某个 UI 功能），应回到提示词对应章节逐条核对是否达成，并把复盘结论同步到任务清单文档（即十.2 的 TASKS.md）；

  - 交付前的最终自查，须对照提示词全文逐节核对一遍。
- **九.4**（L131–135）删除与清理红线（安全红线，任何情况下不得违反），含 4 个子条款：
  - **九.4-a**（L132）：严禁使用任何通配符删除指令（包括但不限于 `*`、`Remove-Item -Recurse`、`rm -rf`、`del *` 等）；清理构建缓存、node_modules、重装依赖等场景同样适用，不得以「重新安装 / 清理缓存」等任何理由放宽。
  - **九.4-b**（L133）：大规模清理场景（如 node_modules、构建缓存这类成千上万文件的目录）不走「逐一删除」的笨办法，也不回退到任何通配符 / 递归删除：优先用包管理器的自修复 / 强制重装命令（如 `pnpm install`、`pnpm install --force`）；确需隔离损坏目录时用「整体重命名挪开」的非破坏方式（如将 node_modules 重命名为 node_modules_broken）后再全新安装；或在交付说明中列为「待清理项」交由用户处理。原则是：宁可换方法，不做大规模删除。
  - **九.4-c**（L134）：确需删除文件时，必须逐一显式指定具体文件的完整绝对路径，严禁对整个父目录执行一键清空。
  - **九.4-d**（L135）：删除文件时必须将文件移动到系统回收站，而不是直接删除；若当前环境无法可靠地把文件移入回收站，则保留该文件并在交付说明中列为「待清理项」交由用户处理，绝不直接删除。
- **九.5**（L136–139）项目目录与版本管理约束，含 3 个子条款：
  - **九.5-a**（L137）：所有工作收拢在一个新建的项目目录内——在当前工作目录下新建一个语义明确的项目子目录（如 `mini-camp-diorama/`，产出实现文档阶段即可先行创建）；项目源码、配置、构建产物与全部文档（DESIGN.md、TASKS.md、DEPENDENCIES.md 等）一律写入该目录，严禁把任何项目文件直接写在当前工作目录下；当前工作目录中已有的其他文件与目录一律不得改动、移动或删除。
  - **九.5-b**（L138）：允许在项目目录内初始化本地 git 仓库，并在实现过程中按合适的颗粒度进行本地提交——例如脚手架搭建完成、单个场景 / 车型完成、某个公共系统完成、文档更新等节点各成一笔提交；提交信息需清晰描述本次变更内容。
  - **九.5-c**（L139）：严禁初始化或配置任何远程仓库，严禁 push 以及 `gh repo create` 等一切对外发布操作；版本管理仅限本地仓库。

## 三、存疑点（原文含糊、疑似边界或需用户拍板处）

1. **六.1 UI 图标的来源未指定**：八.1 要求运行时不依赖网络、八.2 要求贴图用 Canvas / SVG 程序化生成，但原文未说明 UI 的「图标」可否引入第三方图标 npm 包（打包进产物后离线可用），还是应按八.2 的精神用内联 SVG 程序化绘制。需在 DESIGN.md 技术选型中明确并请用户确认。
